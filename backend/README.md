# SpeakUp — بک‌اند

نسخه ۰.۱ · Node.js 20 + TypeScript + Express

## اجرا

```bash
cd backend
npm install
npm run dev          # سرور توسعه روی :8080
npm test             # ۷۹ تست واحد
npm run typecheck    # بررسی نوع بدون تولید خروجی
```

## چرا این انتخاب‌ها

**Node + TypeScript، نه Go.** سند ۰۵ هر دو را پیشنهاد داده بود. Node روی این سیستم نصب بود و برنامه‌نویس شما راحت‌تر بازبینی‌اش می‌کند.

**SQLite، نه PostgreSQL — فعلاً.** سند ۰۵ Postgres را پیشنهاد داده بود، اما Postgres محلی نصب نیست و کد بک‌اند تست‌نشده همان چیزی است که در انتشار می‌شکند. تمام SQL پشت `src/db/index.ts` است و مهاجرت چهار تغییر مشخص دارد که بالای همان فایل مستند شده.

## نکات مهم برای بازبینی

**۱. زنجیره فقط سمت سرور محاسبه می‌شود.** بدنه `check-in` عمداً خالی است: کلاینت نه تاریخ می‌فرستد نه طول زنجیره. تاریخ از `todayInAppTz()` می‌آید. این تنها راه بی‌اثر کردن تقلب با تغییر ساعت گوشی است (سند ۰۳ / F-10). اگر روزی وسوسه شدید تاریخ را از کلاینت بگیرید، کل مکانیزم بی‌معنا می‌شود.

**۲. کد ورود هرگز خام ذخیره نمی‌شود.** فقط `sha256(phone:code)` در دیتابیس می‌نشیند؛ اگر دیتابیس لو برود کدهای فعال قابل استفاده نیستند. تستی هست که این را تضمین می‌کند.

**۳. کد یک‌بارمصرف است** و بعد از ۵ تلاش نادرست قفل می‌شود. دو سد جدا جلوی هزینه را می‌گیرند: ۸۰ ثانیه فاصله بین دو درخواست، و سقف روزانه هر شماره (`SMS_DAILY_LIMIT`، پیش‌فرض ۱۰). فاصله ۸۰ ثانیه به‌تنهایی کافی نیست — با همان فاصله هم می‌شود شبانه‌روز صدها پیامک روی یک شماره فرستاد و هر پیامک پول است.

**۴. `JWT_SECRET` در تولید اجباری است.** `loadConfig` اگر `NODE_ENV=production` باشد و راز کمتر از ۳۲ کاراکتر باشد، بالا نمی‌آید. همچنین `EXPOSE_OTP=1` در تولید خطا می‌دهد.

**۵. قواعد حل تعارض همگام‌سازی عمدی‌اند** و در `src/lib/sync.ts` مستند شده‌اند. مهم‌ترینش: **پیشرفت هرگز عقب نمی‌رود**. اگر گوشی دوم همان درس را ناتمام داشته باشد — حتی با timestamp جدیدتر — وضعیت تمام‌شده پاک نمی‌شود. ۱۵ تست این قواعد را پوشش می‌دهند؛ تغییرشان بدون تغییر تست یعنی از دست رفتن پیشرفت کاربر.

**۶. سرویس پیامک وصل است.** `src/lib/sms.ts` پشت یک واسط نشسته تا تعویض ارائه‌دهنده یک فایل باشد، نه دست بردن در مسیر احراز هویت. سه نکته که در بازبینی مهم‌اند:

- **تولید بدون پیامک واقعی بالا نمی‌آید.** اگر `SMS_PROVIDER` تنظیم نشده یا `console` باشد، `loadConfig` خطا می‌دهد. بدون این محافظ، یک متغیر جاافتاده یعنی سروری که کد می‌سازد و هیچ‌کس پیامکی نمی‌گیرد — خرابی‌ای که فقط از شکایت کاربر فهمیده می‌شود.
- **اگر پیامک نرفت، پاسخ ۵۰۲ است، نه «موفق».** کد ساخته‌شده هم پاک می‌شود تا قطعی سرویسِ ما سهمیه روزانه و ۸۰ ثانیه انتظار کاربر را نسوزاند.
- **کاوه‌نگار روی خطا هم گاهی HTTP 200 می‌دهد.** ملاک، `return.status` داخل بدنه است. تستی هست که این را تضمین می‌کند؛ اگر روزی به `res.ok` بسنده شود، کاربر «کد فرستاده شد» می‌بیند و هیچ پیامکی نمی‌آید.

**⚠️ الگوی پیامک باید به هش ۱۱ کاراکتری اپ ختم شود**، وگرنه SMS Retriever اندروید کد را خودکار پر نمی‌کند و کاربر باید دستی تایپش کند. این متن در پنل کاوه‌نگار ثبت می‌شود، نه در کد.

**۷. رسید خرید سمت سرور سنجیده می‌شود.** اپ فقط `purchaseToken` می‌فرستد؛ نه قیمت، نه تاریخ انقضا، نه اینکه «خرید موفق بود». اگر اپ خودش تصمیم بگیرد، با یک APK دستکاری‌شده اشتراک رایگان می‌شود.

سه قاعده در `src/lib/purchase.ts` که تست دارند و نباید شل شوند:

- **یک رسید فقط یک بار.** ارسال دوباره همان توکن، اشتراک دوم نمی‌دهد (`alreadyRedeemed: true`) و برای حساب دیگر اصلاً کار نمی‌کند.
- **شکست شبکه یعنی رد، نه قبول.** اگر API کافه‌بازار در دسترس نباشد، رسید نامعتبر شمرده می‌شود. برعکسش یعنی هر قطعی، یک پنجره اشتراک رایگان.
- **تمدید از تاریخ انقضای فعلی حساب می‌شود**، نه از امروز؛ وگرنه کاربری که زودتر تمدید می‌کند ضرر می‌کند.

بدون `BAZAAR_ACCESS_TOKEN`، در توسعه هر رسیدی پذیرفته می‌شود (تا بدون حساب کافه‌بازار بشود کل مسیر را تست کرد) و در تولید هیچ رسیدی. قیمت‌ها در `PLANS` همان فایل‌اند، نه در اپ — تغییر قیمت نباید نیازمند انتشار نسخه باشد.
